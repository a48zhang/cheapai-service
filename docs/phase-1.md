# 一期核心目标

状态：2026-09-09 更新。已确定纯 Cloudflare、接受重写后端；上游与下游均支持 OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages，参考 Sub2API 实现透明双向转换，不涉及账号 OAuth。计费采用预付费软卡口和请求后扣费，用户已明确接受少量透支；D1 保存真实账单，KV 适度缓存。

## 产品目标

做出一个可供自用或小团队实际使用的跨协议 API 网关，完成用户注册与邮箱验证、渠道管理、平台 Key 分发、无感协议转换、流式调用、配额控制、准确结算及查询的完整流程。一个渠道由 Base URL、上游 API Key、支持的协议、模型配置及限额构成；客户端不必了解所选上游协议。

一期成功不以页面数量或路由数量衡量，也不承诺复刻 Sub2API 全部功能。

## 范围与验收

| 编号 | 核心目标 | 一期范围 | 验收证据 |
| --- | --- | --- | --- |
| P1-01 | 上游可行性 | 配置 Base URL、API Key、模型及 Chat Completions/Responses/Messages 能力 | 九种上下游组合均验证普通响应、SSE、工具调用与多轮；每种上游协议有真实测试记录 |
| P1-02 | 管理员入口 | 初始管理员配置、登录、退出，普通用户无管理权限 | 未登录与越权请求被拒；过期会话无效 |
| P1-03 | 渠道管理 | 添加、修改、禁用、分组、模型映射、并发上限；支持多个渠道 | 禁用渠道不能通过新的 D1 最终准入，临时获取的租约释放；上游密钥仅管理员配置且不被返回；模型映射正确 |
| P1-04 | 用户与 Key | 管理员创建用户、授额并开放多个分组；用户 Key 选择其中一个组，管理员可撤销 | Key 只在创建时返回明文；不能越权访问其他用户的 Key；撤销后已确认的新准入被拒绝 |
| P1-05 | 网关 | GET /v1/models；POST /v1/chat/completions、/v1/responses、/v1/messages；三协议自动双向转换 | 客户端保持自己的协议；请求、普通响应、SSE、工具 ID、结束原因和 usage 按矩阵通过测试 |
| P1-06 | 调度与并发 | 用户级和渠道级并发可设不限（新建默认不限）、租约、模型路由、基本冷却 | 同用户多 Key 不能绕过总并发；流结束或取消后释放；故障租约可回收 |
| P1-07 | 预付费与账单 | 管理员人工授额、余额软卡口、调用后扣费；允许少量透支；KV 适度缓存 | 负余额真实保留，低余额回源后拒绝新调用；D1 幂等扣费不重复，价格快照可查；缓存失败不丢已提交账单 |
| P1-08 | 运维查询 | 请求状态、耗时、用量、费用、失败原因、结算失败与负余额 | 可从 request_id 串起一次请求；异常结算可发现和追踪 |
| P1-09 | 工程可复现 | 源码、锁文件、D1/DO 迁移、环境配置、测试与部署说明 | 干净环境按说明可构建并部署独立测试环境 |
| P1-10 | 注册方式 | 关闭注册、开放注册、注册码注册三种模式，管理员配置 | 关闭时直接调用接口也失败；开放时无需注册码；注册码模式缺码或无效码不可注册 |
| P1-11 | 注册码管理 | 管理员生成、列表查询、禁用；单次使用、有效期和使用记录 | 同一码并发注册仅一人成功；注册失败不核销；重复邮箱不产生第二个账户 |
| P1-12 | 邮箱验证 | 独立于注册模式的邮箱验证开关；发送、重发、过期和尝试次数控制 | 开启时无有效验证码不能注册；验证码绑定邮箱与注册用途，重发/使用后不可重放；邮件失败不绕过验证 |
| P1-13 | 用户登录与账户 | 至少六位密码登录、退出、当前用户；注册事务内创建零余额与普通用户权限 | 无跨存储初始化；重复注册不重复授额；普通用户不能变管理员；退出会话失效 |

客户端/SDK 版本、上游服务和模型、协议字段与测试用例在 M0 固定；完整方向矩阵见 [协议转换方案](protocol-compatibility.md)。仅支持一种协议的渠道也能服务其他两种下游协议的可映射请求。平台 Key 与上游 Key 是两套独立凭据，用户不能读取或自行指定上游 Key。

注册流程参考 Sub2API。注册模式和邮箱验证是两个独立维度：开放注册与注册码注册都可要求邮箱验证。默认关闭注册，邮箱验证默认开启。注册码只提供注册资格，不承担充值或返佣作用。详细流程见 [注册与身份方案](registration-auth.md)。

## 明确暂缓

- 上游账号 OAuth、订阅凭据导入、令牌刷新、浏览器登录和账号会话粘性。
- Gemini 原生协议、音频、视频、Embeddings、文件管理、图像生成和 Realtime/WebSocket 独立接口。对话中的图片内容映射属于转换矩阵，按上游模型能力验收；不按模型厂商品牌排除。
- 社交登录、支付回调、优惠券、推广返佣、多次使用注册码、密码找回和登录二次验证；注册邮箱验证属于一期。
- 复杂订阅套餐、滚动计费窗口、多级渠道策略与完整运营报表。
- 对原版管理 API 和前端的全面兼容。
- 将现有线上业务或数据库直接切换到新实现。
- 高并发商业规模承诺；容量目标在 M0 基于预期请求量明确，再用负载测试验证。

## 正确性底线

1. 客户端请求 ID 仅用于追踪；网关生成内部请求 ID，用于租约、结算和幂等。
2. D1 是余额和账单的唯一真实数据源；准入允许使用有业务时限的 KV 快照，不保证严格零透支。
3. 充值/授额和扣费在 D1 中原子记账并去重；KV 不执行余额读改写。Key、用户与渠道有效性在发送前由 D1 确认。
4. 已经向客户端输出内容后不自动重放整个上游请求；输出前也只重试明确安全的错误。
5. 客户端取消后尝试取消上游、回收租约；不得假设上游一定立即停止或一定返回最终 usage。
6. 缺失最终 usage 或结算失败分别标记待核对/待结算，有限重试和人工检查；不伪造精确费用，不默认为零。
7. 管理员禁用渠道不追溯取消已准入请求，除非后续显式实现强制终止功能。
8. 创建用户、核销注册码、消费邮箱验证凭证必须原子完成，不能先核销再创建。
9. 注册设置以提交时服务端权威值为准；关闭注册或启用验证码后，旧页面不能绕过新设置。
10. 邮箱唯一性由数据库约束保证；验证码和注册码不明文持久化，不记录到日志。
