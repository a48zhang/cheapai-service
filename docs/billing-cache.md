# 计费与 KV 策略

本文是 [完整技术方案](architecture.md) 第 8–9 章的专题补充。主文档已固定金额规则、原子写入契约、恢复状态与初始缓存开关；下文保留 Sub2API 对照证据。

## 已确认取舍

允许少量透支。默认先充值/授额，再通过预付费卡口；调用完成后按 usage 扣费。并发和缓存可能使余额变负，负数如实保留，余额不足时拒绝后续新请求。

“预付费”是调用资格门槛，不是发行预付卡，也不要求按每笔请求冻结最坏成本。取消额度预留、释放、用户账本 DO 和异步账单投影。

## 对照 Sub2API 的实际实现

已核对固定提交 `ab99d56e9626e6cd731592dae8553c9758a0efa2` 的普通余额路径，结论是“调用前检查资格，发生消费后允许扣成负数”，不是每次调用预先冻结预算。

| 原版位置 | 已核对行为 | 本工程对应 |
| --- | --- | --- |
| billing_cache_service.go:310–350、863–896 | 优先读缓存，未命中回源数据库；余额 <= 0 或低于配置 MinimumBalanceReserve 时拒绝 | KV 快照/回源 + 可配置准入门槛；不做预算冻结 |
| usage_billing_repo.go:243–272 | 先执行带 balance >= amount 条件的扣款；余额不足时再执行不带余额条件的扣款，允许结果为负 | D1 原子扣款允许负数，不因余额不足拒绝登记已发生消费 |
| usage_billing_repo.go:174–189 | 返回 NewBalance，并以 BalanceOverdrafted 标识该笔扣费时余额不足 | 结算结果/日志记录扣后余额和透支标记 |
| usage_billing_repo.go:35–89 | 去重键与计费效果置于同一数据库事务；重复请求不再应用效果 | 唯一结算键 + D1 原子账单/扣款 |
| gateway_usage_billing.go:427–442 | 扣后余额低于资格门槛时失效余额缓存；仍可用时更新缓存 | 越过门槛尽力失效 KV、回源判断；不照搬 Redis 原子减缓存 |

原版回归测试包含：缓存余额 0.50，实际费用 0.75，数据库余额 -0.25；扣款完成后失效缓存，再次资格检查从数据库读到负余额并拒绝。这里来自源码/测试阅读，未在本机运行该 Go 测试。

我们沿用其业务语义：已准入调用的实际费用要完整入账，余额可为负；接下来的新请求在检查到不足时拒绝。不把“透支”当作扣款失败，不把余额强行截为零，也不截断正在进行的流。

原版还包含批量图片预冻结等其他计费路径，它们不属于当前一期范围，不能从这些特殊路径推导普通文本请求必须冻结余额。

Redis 缓存扣减在原版使用 Lua 原子操作。Cloudflare KV 没有等价原子增减，因而只复用缓存优先的思路，继续采用短期快照和 D1 正式扣款。KV 失效不保证跨地区立即可见，余额不足后的阻断窗口还受业务快照有效期和在途请求影响，不宣称与 Redis 完全同等。

## 卡口

- 配置 admission_min_balance，默认以余额大于零作为最简单门槛。可按模型配置更高的准入门槛，但它不是单次成本预留。
- fresh 的高余额缓存可以通过软卡口；低余额、负余额、快照过期/格式不合法或缓存失败，回源 D1。
- D1 余额仍低于门槛时返回余额不足；充值后低余额缓存不能持续误拒，先回源再决定。
- 执行中的调用不因别的并发请求把余额扣成负数就中断。
- 请求和输出大小、输出 token 上限、用户并发/RPM 与昂贵模型权限共同控制风险。少量透支是运营容忍，不承诺绝对金额上限；高成本请求和较长在途时间仍可能放大透支。
- 不默认在数据库故障时放行；允许透支和允许不计费/不鉴权是两回事。

## 缓存内容

首版默认启用路由/价格缓存，余额 KV 提供开关、初始关闭；D1 准入查询已有余额时直接使用。以下余额快照规则在启用开关后适用，是否启用按减少的读取和总延迟判断。

| 内容 | 策略 |
| --- | --- |
| 路由候选、模型映射、定价配置 | cache-aside，含配置版本；每个请求固定自己的价格快照 |
| 余额快照 | balance_units、observed_at、schema_version；仅作软卡口/显示优化 |
| 公开注册设置与模型展示 | 可缓存显示；提交与安全校验仍查 D1 |
| Key/用户/渠道启用状态 | 缓存可用于定位；发送前 D1 再确认，缓存不能最终授权 |
| 账单、扣款、验证码/注册码消费 | 仅 D1；不在 KV 读改写 |

余额快照初始业务有效期可设为 15 秒，低余额回源阈值为可配置安全余量，实施前用负载与透支数据调节。这里的 15 秒是应用层检查 observed_at 的规则，不是 KV 全局一致性承诺。

observed_at 来自 D1 快照读取开始时刻，写入 KV、复制或重试时不得刷新它。读到物理上仍缓存但业务上过期的值时直接回源，不采用 stale-while-revalidate 放行。并发回填可能覆盖较新缓存，KV 没有 CAS；不得因此覆盖 D1 或把旧快照伪装新鲜。

用于回填余额和执行安全校验的 D1 读取需选择主库或有相应当前性保证的会话；不能给滞后读副本的旧余额打上新的 observed_at。KV 的物理 TTL/cacheTtl 遵守平台限制，业务过期时间独立检查。

## 失效、写频率与收益

Cloudflare KV 的跨地区更新可能需要 60 秒或更久；删除同样不是全局立即可见。对余额必须同时检查业务时间戳，不能只设 TTL 后承诺立即阻断。

同一个 KV key 的写入限制为每秒一次。避免每个请求结束都 put 最新余额，也不向 KV 累加消费。默认在回源/失效后按需回填，使用保守节流和有限重试；多地区回填冲突或 429 当作缓存失败，使用 D1 结果继续。不要为保证缓存写成功再造一个持久化同步系统。

扣费越过低余额门槛、充值/授额和配置变更后可尽力失效或回填。缓存更新失败不让充值/扣费失败；热点用户余额经常过期且回填收益低时，关闭该用户或全局余额缓存。路由与价格等低频变更数据是 KV 的主要受益者。

D1 仍有请求登记和结算写入，缓存不解决写吞吐。若一次合并查询已获得真实余额，优先使用它，不再额外读 KV；上线用命中率、总调用数和延迟判断是否保留余额快照。

## 结算

调用前写 requests(request_id, user_id, channel_id, model, price_snapshot, status)。接口间转换只影响格式，账单从实际上游 usage 提取一次。

调用结束以唯一结算键插入 billing_entries，并在同一 D1 原子操作内执行 balance = balance - cost、更新请求状态。重复结算不会重复扣款；不能用“余额不足”拒绝登记已经发生的消费。价格和金额使用定点整数/字符串，明确单位及取整规则，不用浮点累计。

实施基线为 1 USD = 100,000,000 units，金额限定在 D1/JS 可安全往返的整数范围内，API 输出十进制字符串；互斥 token 计费桶汇总后 half-up 到一个 unit。账单插入触发原子余额增减和请求状态更新；重复唯一键不再执行效果，必须比对原 fingerprint。消费账单只追加，人工纠错使用独立 adjustment。

不逐 token 写库，不把所有账单先放 KV 再批量导出。管理员授额同样有唯一操作 ID 和账单明细；统计直接查 D1，用索引和分页控制查询。

## 不确定结果

- 正式账单已提交、响应丢失：按相同 request_id 查询/重试，不能再扣一遍。
- usage 已收到但 D1 暂时失败：当前执行中有限重试；若能持久化 usage，则 Cron 可幂等补结。
- Worker 终止且 usage 未持久化：保留调用前请求记录，标记待核对；不能根据一次成功 HTTP 状态猜精确费用。
- 上游未返回最终 usage：使用明确的 unknown 状态，人工调整需留审计；不静默按零费结算或伪造 token 数。

初版不承诺零漏单；必须让结算失败和未知用量可见。若生产需要更强投递保证，再以数据为依据增加可靠结算机制。

## 验收

- D1 扣费与账单一致，同一内部 request_id 的结算重试不会重复扣款；客户端再次发起生成是新调用，按新请求计费。
- 对照原版回归：余额 0.50、费用 0.75，结算得到 -0.25 且记录透支；余额门槛检查确认不足后拒绝下一请求，充值后可以恢复。
- 并发导致负余额允许；低余额和缓存过期回源后停止新准入。
- KV 错误、旧值覆盖、新建 key 的负缓存、写入 429 均不影响真实账单。
- 充值后旧低余额缓存可回源放行；撤销 Key 即使缓存仍在也不能新准入。
- 输出限制、并发限制、异常账单和负余额指标有测试与管理可见性。
